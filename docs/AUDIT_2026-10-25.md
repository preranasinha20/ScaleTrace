## B. Deep-learning status

### What exists [Verified]
- A directed GraphSAGE GNN in plain PyTorch (`ml/model.py`, ~54k parameters), trained with a listwise
  ranking loss (`ml/train.py`) over six feature groups (`ml/features.py`).
- A synthetic generator, runtime collection, an experiment harness with baselines and ablations, and
  checkpoints from v2 and v3.
- `diagnose --model` uses the GNN as the ranker and attaches an explanation.

### What does not exist
- **A valid trained model.** The v1, v2 and v3 experiments all hit perfect scores immediately:

  | Run | Cause of the perfect score | Detected by |
  |---|---|---|
  | v1 | The root cause was the handler in 6 of 7 defect kinds | Proximity baseline |
  | v2 | Function names (`collect_*`) leaked the label | Analysis of the names |
  | v3 | Template fingerprints (per-function counts of queries/loops/calls are unique per template role) | `static_no_code` **and** `runtime_only` both at 1.00 |

  v3 baselines (held-out style B, n=100), Top-1 / MRR: random 0.00 / 0.39, proximity 0.34 / 0.51,
  rules_only 0.63 / 0.80, heuristic_static 0.63 / 0.79, heuristic_combined 0.61 / 0.73. So the task
  is not trivial for the heuristics, but the GNN memorizes the templates.
- A useful explainer (currently degenerate).
- A second learned task (node-level risk) and any learned path prediction.
- Pretrained code-encoder results.

### Answers to the ten questions

1. **Is a model implemented or trained?** Implemented: yes. Trained: yes. **Validly evaluated: no.**
   The training data is solvable by template shortcuts, so the scores say nothing about real code.
2. **What remains?** (a) A generator or data source without per-template fingerprints. (b) A working
   explainer. (c) A node-risk head. (d) GNN as the default ranker once it passes evaluation.
   (e) Path labels and a path metric. (f) Evaluation on the team benchmark.
3. **Inputs and outputs.**
   - *Graph:* the knowledge graph of one app (nodes: endpoints, functions, database, external services).
   - *Edges:* routes_to, depends_on, calls, queries, calls_external, as directed edges with weight
     1 + in_loop + observed.
   - *Node features* (`ml/features.py`):
     - type one-hot (4)
     - structure (12): log loc, loops, depth, calls, calls in loop, DB ops (in loop), external (in loop), unresolved calls, async, handler
     - rules (7): per-rule finding counts, max severity
     - symptom conditioning (4)
     - runtime at the symptom endpoint (8): executed, call-count growth, attributed-query growth, query share, log calls, log queries, endpoint metric growth
     - code embedding (32)
   - *Target:* binary root-cause label on function nodes.
   - *Output:* one logit per node; softmax over the symptom's candidate set.
   - *Loss:* listwise `-log Σ_pos softmax(candidates)`.
   - *Metrics:* Top-1, Top-3, MRR with expected-rank tie handling.
4. **What is learned?** Today: **root-cause ranking given a symptom endpoint**. Recommended: add a
   multi-task **risky-node classification** head (symptom-independent: "this function is an injected
   scalability defect"). That way the model also contributes in static-only use. Path prediction stays
   derived: the shortest observed-preferred path to the ranked node.
5. **How evidence is combined:** concatenation of feature groups per node, then 3 rounds of message
   passing with separate predecessor and successor aggregation. Static findings enter as raw counts,
   never as statuses. Runtime enters relative to the symptom endpoint. Code enters as a frozen embedding.
6. **Leakage control:** split by application, never by node or symptom. Hold out a code style. Planned:
   hold out a template family / defect kind and the whole team benchmark (test only). Names are
   neutral (done). Planned: near-duplicate check between generated and benchmark code, and a
   fingerprint check (section D).
7. **Explainability:** GNNExplainer-style edge and feature masks exist but collapse to ~1.0 everywhere
   (masks start at sigmoid(1), the entropy term pushes them up, and a saturated model gives no gradient).
   Fix: start the masks at 0.5, use stronger size regularization, and explain the logit margin over the
   runner-up. Add gradient×input as a cheap deterministic check, plus a counterfactual "drop the runtime
   group, re-rank" check. Limitation: these explain the *model*, not the program; there is no causal claim.
8. **Hardware:** CPU is enough. The GNN has ~54k parameters, and a full 18-model experiment ran in
   minutes. A frozen pretrained encoder (CodeBERT/UniXcoder, ~125M parameters) costs roughly 0.1–0.5 s
   per function on CPU, cached once; that's an estimate, not measured here. A GPU is unnecessary unless
   the encoder is fine-tuned, which is not recommended at this data scale. Dependencies: torch (CPU),
   numpy, optional transformers.
9. **Simplest defensible implementation:** keep the current GNN with a frozen encoder (no fine-tuning).
   Fix the data (section D), fix the explainer, add the node-risk head, then run the honest comparison
   against the heuristics on the team benchmark. A negative result is acceptable if it's measured.
10. **Rule-based vs learned decisions.**
    - *Stays rule-based:* static candidate detection, severity, runtime measurement, symptom detection,
      every **status transition** (correlated / not_confirmed), and the evidence text.
    - *Learned:* (a) ranking of probable-cause nodes for a symptom, (b) node-level risk prediction,
      (c) which evidence to weight (replacing the hand-set w_s / w_d / w_p).
    - The model never changes a finding's status and never creates runtime evidence.

## D. Dataset and training plan

### Role of the 25 good + 25 bad codebases
1. **Never used for training.** Recommended split (stratified good/bad, grouped by author and template
   family): **dev 5 good + 5 bad** for sanity checks and threshold selection only, **test 20 + 20**
   untouched until the final run. If fewer apps are accepted, keep dev ≈ 20% and report actual counts.
2. **Training data comes from:**
   - (a) a **redesigned synthetic generator**
   - (b) **[Recommendation] defect injection into other public FastAPI repos** (not among the 25;
     licence permitting). Real code supplies realistic structure, and the injection supplies exact labels.

### Generator redesign (what v1–v3 taught us)
3–4. The generator must break per-role fingerprints:
   - **Shared building blocks:** the same code fragments (extra queries, loops over query results, small
     loops, helper calls) appear in root causes, decoys and clean functions, so no count or shape
     identifies a role.
   - **Hard decoys:** structurally identical to defects but bounded at runtime (loop over a query that
     returns ≤3 rows by design; N+1 over a relationship that is eagerly loaded elsewhere). Only runtime
     or deep context distinguishes them.
   - **Root causes without the "usual" shape:** loops in comprehensions, `while`, nested helpers, class
     methods, `select()`-style SQLAlchemy 2.0, async sessions, SQLModel.
   - **Variable depth (0–3), fan-out, and multiple defects** sharing callees.
   - **Random amounts of benign code** around everything.
5. **Labels:** the generator/injector records the defect location, so labels are exact at node and
   application level. **Additionally keep only examples whose runtime run actually shows the symptom**
   ("runtime-verified"), and record unverified ones separately.
6–7. **Diversity and shortcut checks** (automated, run before every experiment):
   - a node-only baseline (MLP / logistic regression on node features, no message passing)
   - `static_no_code` and `runtime_only` ablations
   - the proximity baseline
   - an identifier-permutation test (rename everything; scores must not change)
   - a fingerprint audit (does any single feature perfectly separate root from non-root?)
   - **If a trivial model reaches ~1.0, the dataset is rejected.**
8. Benchmark split: see point 1.
9. **Near-duplicate prevention:** AST-normalized token-shingle similarity between every generated or
   injected training app and every benchmark app; report the maximum. A bad app derived from a good
   app stays in the same split. Generator authors should not copy benchmark code, and the generator
   should be frozen before the test set is opened.
10. **Good repos that contain target defects or won't run:** screen with ScaleTrace plus manual review.
    A confirmed target defect is either recorded as a labelled positive in that app ("good" = suitable
    reference, not defect-free) or the app is excluded, with the reason logged. Apps that can't be run
    stay in the **static-only** evaluation with `runtime_status: unavailable`. Never drop them silently.
11. **Shared format** [Recommendation]: one directory per app plus `scaletrace_benchmark.json`,
    replacing/merging today's `scaletrace_groundtruth.json` and `scaletrace_rootcause.json`:

```json
{
  "schema_version": "1.0",
  "app_id": "bad-07",
  "kind": "bad",
  "origin": {"source": "team", "author": "…", "template_family": "orders-v2", "derived_from": "good-03",
             "repo_url": null, "commit": null, "license": "MIT"},
  "split": "test",
  "run": {"workload": "scaletrace_workload.json", "runtime_status": "verified | failed | not_attempted",
          "notes": ""},
  "defects": [
    {"defect_id": "bad-07-d1", "rule_id": "DB-001", "category": "repeated_database_queries",
     "file": "app/routers/orders.py", "function": "list_orders", "line_start": 41, "line_end": 44,
     "endpoint": "GET /orders", "symptom_kind": "query_growth",
     "root_cause_functions": ["app.routers.orders:list_orders"],
     "path": ["endpoint:GET /orders", "function:app.routers.orders:list_orders", "resource:database"],
     "verification": {"static": "verified", "runtime": "verified", "verified_by": "…", "date": "…"}}
  ],
  "known_non_defects": [{"file": "…", "line": 0, "rule_id": "MEM-001", "reason": "bounded by design"}]
}
```

Derived artifacts are cached per app under `.scaletrace/` (analysis.json, graph.json, runtime.json),
so the rule engine, graph, trainer and evaluator all read the same data.
